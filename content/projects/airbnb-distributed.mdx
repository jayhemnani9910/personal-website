  keyDecisions:
    - decision: "Run the booking flow through Kafka instead of direct calls"
      reasoning: "The lab asked for it, and the reasoning holds: with synchronous calls, if one service is down the caller fails. With topics and consumer groups, a consumer can be slow or briefly offline and catch up from the log."
      alternatives: "Direct REST calls between services (tight coupling, cascading failures)."
    - decision: "Isolate the AI concierge as its own service"
      reasoning: "The LLM stack (LangChain plus a local Ollama model) is heavy and has nothing to do with booking correctness. Its own FastAPI service keeps it out of the booking code."
      alternatives: "Call the LLM from the frontend or a core service (drags the model into the booking path and the client bundle)."
    - decision: "Keep running when Kafka is absent"
      reasoning: "A broker isn't always there in local development. The consumers log a warning and carry on, so you can work on the rest without the full event bus."
      alternatives: "Require Kafka at boot (blocks local work unless a broker is running)."

        async function setupKafkaConsumer() {
          const consumer = await kafka.createConsumer('booking-status-sync-group');
          if (!consumer) {
            logger.warn('Kafka consumer not created - running without Kafka');
            return;   // degrade gracefully in local dev
          }

          await kafka.subscribe('booking-updates', async (updateData) => {
            // apply the status update to this service's MongoDB
          });

          await kafka.subscribe('booking-requests', async (bookingData) => {
            // create the booking; on error, rethrow to trigger Kafka retry
          });

          await kafka.startConsumer();
        }
      explanation: "Two topics on one consumer group, and if there's no broker it logs and carries on. The retry the comment mentions doesn't happen, because the shared wrapper catches the error first."
