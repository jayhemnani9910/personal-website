Everything is containerized: Docker Compose for local development and a full set of Kubernetes manifests (services, MongoDB, Kafka, Ollama, config, secrets) for cluster deployment, with Playwright, Postman, and JMeter covering end-to-end, API, and load testing."

  keyDecisions:
    - decision: "Communicate through Kafka instead of direct service-to-service calls"
      reasoning: "Synchronous calls between services couple their availability: if one is down, the caller fails. Routing booking events through Kafka topics with consumer groups means a service can be slow or briefly offline and catch up from the log, which is the whole reason to go microservices in the first place."
      alternatives: "Direct REST calls between services (tight coupling, cascading failures); a shared database (re-couples the services through their data)."
    - decision: "Isolate the AI concierge as its own service"
      reasoning: "The LLM dependency (LangChain + a local Ollama model) is heavy and unrelated to booking correctness. Putting it behind its own FastAPI service keeps that dependency out of the core path, so the booking system does not inherit the AI service's footprint or failure modes."
      alternatives: "Call the LLM from the frontend or a core service (drags the model dependency into the booking path and the client bundle)."
    - decision: "Degrade gracefully when Kafka is absent"
      reasoning: "A broker is not always available in local development. The booking service logs a warning and runs without Kafka rather than refusing to start, so developers can work on the rest of the system without standing up the full event bus."
      alternatives: "Hard-require Kafka at boot (blocks all local work on the service unless a broker is running)."

          const consumer = await kafka.createConsumer('booking-status-sync-group');
          if (!consumer) {

          await kafka.subscribe('booking-updates', async (updateData) => {
            // apply the status update to this service's MongoDB
          });

          await kafka.subscribe('booking-requests', async (bookingData) => {
            // create the booking; on error, rethrow to trigger Kafka retry
          });

          await kafka.startConsumer();
        }

A team-built Airbnb-style booking platform, internally called Voyage, that evolved from a monolith into an event-driven microservices system. A React/Redux/Vite frontend sits over four Node/Express services (traveler, owner, property, booking), each with its own MongoDB, communicating through Kafka topics with consumer groups and retry rather than direct calls. A separate Python FastAPI service runs a local Ollama model through LangChain to generate JSON travel itineraries, kept isolated from the booking path. The whole system ships with Docker Compose for local runs and a full set of Kubernetes manifests, plus Playwright, Postman, and JMeter for end-to-end, API, and load testing.
