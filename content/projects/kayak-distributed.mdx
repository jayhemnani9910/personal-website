Tier 2 is a set of Node/Express services behind an API gateway that does JWT authentication, rate limiting, and routing: a user service, a search service backed by MongoDB and cached in Redis, and a booking service that does transactional inserts and inventory decrements. Tier 3 is the data layer, MySQL for OLTP (users, bookings, billing, listings), MongoDB for analytics and event logs, and Redis for caching. Alongside sits a Python FastAPI AI service that runs a concierge chat agent and a background deals-scoring worker, and exposes bundles, price-analysis, watches, and quotes APIs over REST and WebSockets. The AI service has its own supporting pieces: a semantic cache that reuses LLM responses for similar queries, a rule-based intent parser with optional OpenAI enhancement, and a Kafka client that can run in-memory or against a real broker through a shared interface."

  keyDecisions:
    - decision: "Split the data tier by workload"
      reasoning: "Bookings need transactions and joins (MySQL), analytics and logs are append-heavy and schema-flexible (MongoDB), and repeated searches just need to be fast (Redis). Using one database for all three would compromise at least one of those jobs, so each store is matched to its workload."
      alternatives: "A single database for everything (transactions and analytics and caching all fighting in one engine)."
    - decision: "Put a semantic cache in front of the LLM"
      reasoning: "Travel queries repeat with small variations. Embedding each query and returning a cached answer when similarity clears a threshold (0.85) avoids paying for an LLM call on every near-duplicate, which matters for both latency and cost."
      alternatives: "Exact-match caching (misses paraphrases); no cache (an LLM call for every query, however similar)."
    - decision: "Hide Kafka behind an interface with an in-memory implementation"
      reasoning: "On a team, not everyone can stand up a broker on day one. A KafkaInterface with an in-memory queue lets each person develop and test against simulated topics, then switch to the real broker by changing config, with no code changes."
      alternatives: "Require a real Kafka broker for any local work (blocks teammates and slows iteration)."

A team-built, 3-tier travel metasearch and booking platform modeled on Kayak (flights, hotels, car rentals). A React client talks through an API gateway (JWT auth, rate limiting, routing) to Node/Express middleware services, user, search (MongoDB + Redis cache), and booking (transactional, with inventory control), over a data tier that splits work across MySQL (OLTP), MongoDB (analytics and logs), and Redis (caching). A separate Python FastAPI service adds the AI layer: a concierge chat agent, deal scoring, and bundle and price-analysis APIs, fronted by a semantic cache that reuses LLM responses for similar queries and a rule-based intent parser that uses OpenAI only when available. Kafka carries cross-service events, with an interface-based in-memory implementation for local development.
