  keyDecisions:
    - decision: "Split the data tier by workload"
      reasoning: "Bookings need transactions and joins, so MySQL. Logs and analytics are append-heavy and change shape, so MongoDB. Repeat searches just need to be fast, so Redis. One database for all three would have compromised at least one job."
      alternatives: "A single database for everything (transactions, analytics and caching all fighting in one engine)."
    - decision: "Put a semantic cache in front of the LLM"
      reasoning: "Travel questions repeat with small variations. Embedding each question and reusing the parsed intent when similarity clears a threshold avoids an LLM call for near-duplicates, which helps both speed and cost."
      alternatives: "Exact-match caching (misses rephrased questions); no cache (an LLM call for every question, however similar)."
    - decision: "Start Kafka work on an in-memory stand-in"
      reasoning: "Not everyone has a broker running on day one. An in-memory queue let a teammate build and test the AI side against simulated topics first. The plan was a swap to a matching RealKafka class, but that class never got written, and the deal agents use separate wrappers around the real client."
      alternatives: "Require a real Kafka broker for all local work (blocks teammates and slows everything down)."
