  architecture: "ModelPipeline is designed to run four model stages in one of three modes: sequential, threaded parallel, or adaptive based on available resources, with GPU fallback, timeouts and retries. The stages are a hand-written RF-DETR, a hand-written SAM2 with a tracker, a hand-written SigLIP text-image matcher, and a ResNet jersey classifier. ResultFusion then merges their outputs under a selectable strategy, grouping detections by spatial proximity and applying temporal consistency. Config comes from validated YAML through a ModelConfigManager and a registry. The yt/ tool is separate: its scanner, tracker and Q&A prompts write results into SQLite, and a small script queries them."

  keyDecisions:
    - decision: "A configurable framework instead of one hard-wired pipeline"
      reasoning: "The research question was which combination works, so I designed around a registry and validated presets. In hindsight, this was building the lab before owning a single working instrument."
      tradeoff: "A lot of abstraction and about 34,000 lines of Python, with no trained model underneath to justify it."
    - decision: "SigLIP zero-shot identification over a trained roster classifier"
      reasoning: "Text-image matching should identify players without labelling data for every team. That's the appeal, and it only pays off with real weights."
      tradeoff: "Likely less precise than a roster-trained model. Neither has been measured here."
    - decision: "Selectable fusion strategies rather than one fixed rule"
      reasoning: "The thinking: confidence-based when one model dominates, temporal consistency for video, voting when models disagree. Exposing all seven would let each experiment choose."
      tradeoff: "The caller has to know which fits. With no real outputs to fuse, none of the seven has earned its place."
    - decision: "Sequential, parallel, and adaptive execution modes"
      reasoning: "Four heavy models won't fit every GPU at once, so the design can run them one at a time, threaded, or based on available resources."
      tradeoff: "Parallel mode adds threading and memory complexity, and I built it before there was anything heavy to run."

        class ExecutionMode(Enum):
            SEQUENTIAL = "sequential"   # models one after another
            PARALLEL = "parallel"       # models simultaneously
            ADAPTIVE = "adaptive"       # choose from available resources

        @dataclass
        class PipelineConfig:
            execution_mode: ExecutionMode = ExecutionMode.SEQUENTIAL
            max_workers: int = 4
            batch_size: int = 8
            enable_gpu_fallback: bool = True
            timeout_seconds: int = 60
            retry_count: int = 2
            memory_limit_gb: float = 8.0

        class ModelPipeline:
            """Orchestrates RF-DETR, SAM2, SigLIP, and ResNet with scheduling,
            memory management, and fallback strategies."""
      explanation: "This is the shape of the idea: pick a mode, set limits, and let one slow model fail without taking the run down. Read the docstring as intent, since no trained versions of these models are in the repo."
