tech: ["SQL", "MySQL"]
challenge: "The tables are the easy part. The hard part is the relationships: one person on many cases in different roles, documents that expire on their own schedules, and a history of status changes that has to survive. The job was to model all of that without copying a person's details around."
solution:
  - "An ERD turned into SQL DDL, with indexes for the frequent lookups, a console for CRUD, and a stored procedure that creates a case and its primary applicant in one transaction."
impact:
  - "A cleaner data model, with a junction table for who plays which role and an audit trail for status changes. It's student work and I have no benchmarks to show, so the index choices are design reasoning, not measured wins."
deepDive:
  context: |
    Immigration case data looks like a list of forms until you try to normalize it. The schema has to handle:

    - Several people per case (applicants, dependents, sponsors)
    - Different case types (family-based, employment-based, asylum, and so on)
    - Documents that get submitted, expire and get renewed
    - Deadlines and status changes
    - A history of what changed and when

  architecture: |
    **The design**

    Normalized to 3NF, with one deliberate exception for a counter.

    1. **Core tables:**
       - `persons` - one row per person, whatever their role
       - `cases` - case metadata, type and status
       - `documents` - documents and their expiry dates
       - `case_persons` - who is on which case, and as what

    2. **Supporting tables:**
       - `case_status_history` - the audit trail
       - `document_types` and `case_types` - lookup tables

    3. **Indexes:**
       - `(case_id, person_id, role)` for relationship queries
       - `(expiration_date, status)` for deadline checks
       - `(last_name, first_name)` for name lookups

  components: |
    **1. Schema**
    - Tables with PRIMARY KEY, FOREIGN KEY, NOT NULL and ENUM constraints, plus indexes and views for common queries

    **2. CRUD**
    - Parameterized procedures, with transactions around multi-table work like creating a case and its primary applicant together

    **3. Console**
    - Data entry and retrieval, pre-built queries like case search and expiring documents, and an export for reporting

    **4. Integrity**
    - Foreign keys, automatic `created_at` and `updated_at` timestamps, and CASCADE or RESTRICT chosen per relationship

  dataFlow: |
    **1. Creating a case:**
    ```
    User Input → Validate Person Data → Insert/Update persons table
              → Create case record in cases table
              → Link persons to case via case_persons junction table
              → Initialize case_status_history with "OPEN" status
    ```

    **2. Submitting a document:**
    ```
    Document Upload → Validate document type against document_types
                   → Insert into documents table with case_id reference
                   → Calculate expiration date based on document type
                   → Update case status if all required documents submitted
    ```

    **3. Changing a status:**
    ```
    Status Change Request → Validate allowed transitions (business rules)
                         → Update cases.status field
                         → Insert audit record in case_status_history
                         → Trigger notifications if needed (via application layer)
    ```

    **4. Common queries:**
    - **Expiring documents:** index scan on `idx_expiration` for `expiration_date BETWEEN NOW() AND NOW() + 30 DAYS`
    - **Case details:** join cases, case_persons and persons
    - **Person history:** join persons, case_persons and cases

  keyDecisions:
    - decision: "Keep person data normalized, but store a case count on persons"
      rationale: "Person data rarely changes and gets read a lot. Storing active_case_count saves a COUNT on every listing."
      tradeoff: "Every case change has to keep active_case_count in step; a missed update shows a wrong count until it is recomputed."

    - decision: "A case_persons junction table with a role enum (applicant, dependent, sponsor, attorney)"
      rationale: "One person can hold several roles on the same case, like sponsor and attorney, and the schema stays clean."
      tradeoff: "The role list is an ENUM, so a new role is a schema change (ALTER TABLE), not a row."

    - decision: "Store issue_date and expiration_date instead of calculating them"
      rationale: "Document types have different validity periods and some get extended. A stored date makes deadline checks an index lookup."
      tradeoff: "An extension is an update to the stored date, and nothing in the schema stops a stored date from disagreeing with its document type's validity period."

    - decision: "A case_status_history table, not a JSON field on cases"
      rationale: "History stays queryable with plain SQL, including range questions like \"all cases that were pending in Q2 2023\"."
      tradeoff: "Every status change is two writes inside one transaction, and a case's history is a join away."

    - decision: "MySQL with InnoDB"
      rationale: "Foreign keys, transactions and row-level locking come built in, and a half-written case is the thing to avoid."
      tradeoff: "The schema leans on MySQL specifics (ENUM columns, ON UPDATE CURRENT_TIMESTAMP), so moving to another database is a rewrite of those parts."

    - decision: "utf8mb4 for all text"
      rationale: "Names and addresses come in many languages. José and Müller should come back out as José and Müller."
      tradeoff: "A character takes up to four bytes, so long indexed VARCHAR columns reach InnoDB's index-length limit sooner."

        -- Person entity (normalized to avoid duplication)
        CREATE TABLE persons (
          person_id INT PRIMARY KEY AUTO_INCREMENT,
          first_name VARCHAR(100) NOT NULL,
          last_name VARCHAR(100) NOT NULL,
          date_of_birth DATE NOT NULL,
          nationality VARCHAR(100),
          passport_number VARCHAR(50) UNIQUE,
          email VARCHAR(255),
          phone VARCHAR(20),
          active_case_count INT DEFAULT 0, -- Denormalized for performance
          created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
          updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
          INDEX idx_name (last_name, first_name),
          INDEX idx_dob (date_of_birth)
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

        -- Case entity
        CREATE TABLE cases (
          case_id INT PRIMARY KEY AUTO_INCREMENT,
          case_number VARCHAR(50) UNIQUE NOT NULL,
          case_type_id INT NOT NULL,
          status ENUM('OPEN', 'PENDING', 'APPROVED', 'DENIED', 'CLOSED') DEFAULT 'OPEN',
          filing_date DATE NOT NULL,
          target_completion_date DATE,
          priority ENUM('LOW', 'MEDIUM', 'HIGH', 'URGENT') DEFAULT 'MEDIUM',
          created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
          updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
          FOREIGN KEY (case_type_id) REFERENCES case_types(case_type_id),
          INDEX idx_status_date (status, filing_date),
          INDEX idx_completion (target_completion_date)
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

        -- Many-to-many relationship with role differentiation
        CREATE TABLE case_persons (
          case_person_id INT PRIMARY KEY AUTO_INCREMENT,
          case_id INT NOT NULL,
          person_id INT NOT NULL,
          role ENUM('APPLICANT', 'DEPENDENT', 'SPONSOR', 'ATTORNEY') NOT NULL,
          is_primary BOOLEAN DEFAULT FALSE,
          relationship VARCHAR(50), -- e.g., "spouse", "child", "employer"
          created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
          FOREIGN KEY (case_id) REFERENCES cases(case_id) ON DELETE CASCADE,
          FOREIGN KEY (person_id) REFERENCES persons(person_id) ON DELETE RESTRICT,
          UNIQUE KEY unique_case_person_role (case_id, person_id, role),
          INDEX idx_person_cases (person_id, case_id)
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

        -- Document tracking with expiration management
        CREATE TABLE documents (
          document_id INT PRIMARY KEY AUTO_INCREMENT,
          case_id INT NOT NULL,
          document_type_id INT NOT NULL,
          document_number VARCHAR(100),
          issue_date DATE NOT NULL,
          expiration_date DATE,
          file_path VARCHAR(500),
          status ENUM('PENDING', 'SUBMITTED', 'APPROVED', 'REJECTED', 'EXPIRED') DEFAULT 'PENDING',
          created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
          updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
          FOREIGN KEY (case_id) REFERENCES cases(case_id) ON DELETE CASCADE,
          FOREIGN KEY (document_type_id) REFERENCES document_types(document_type_id),
          INDEX idx_expiration (expiration_date, status),
          INDEX idx_case_docs (case_id, document_type_id)
        ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

        -- View for complete case information
        CREATE VIEW v_case_details AS
        SELECT
          c.case_id,
          c.case_number,
          ct.case_type_name,
          c.status,
          c.filing_date,
          c.target_completion_date,
          p.person_id,
          CONCAT(p.first_name, ' ', p.last_name) AS person_name,
          p.nationality,
          cp.role,
          cp.is_primary,
          cp.relationship,
          COUNT(DISTINCT d.document_id) AS total_documents,
          COUNT(DISTINCT CASE WHEN d.status = 'APPROVED' THEN d.document_id END) AS approved_documents,
          MIN(d.expiration_date) AS next_expiration
        FROM cases c
        INNER JOIN case_types ct ON c.case_type_id = ct.case_type_id
        LEFT JOIN case_persons cp ON c.case_id = cp.case_id
        LEFT JOIN persons p ON cp.person_id = p.person_id
        LEFT JOIN documents d ON c.case_id = d.case_id
        GROUP BY c.case_id, p.person_id, cp.case_person_id;

        -- Query to find cases needing attention (expiring documents)
        SELECT
          c.case_number,
          c.status,
          p.first_name,
          p.last_name,
          dt.document_type_name,
          d.expiration_date,
          DATEDIFF(d.expiration_date, CURDATE()) AS days_until_expiration
        FROM documents d
        INNER JOIN cases c ON d.case_id = c.case_id
        INNER JOIN case_persons cp ON c.case_id = cp.case_id AND cp.is_primary = TRUE
        INNER JOIN persons p ON cp.person_id = p.person_id
        INNER JOIN document_types dt ON d.document_type_id = dt.document_type_id
        WHERE d.expiration_date BETWEEN CURDATE() AND DATE_ADD(CURDATE(), INTERVAL 30 DAY)
          AND d.status NOT IN ('EXPIRED', 'REJECTED')
          AND c.status NOT IN ('CLOSED', 'DENIED')
        ORDER BY d.expiration_date ASC;

    - title: "Creating a case in one transaction"
      language: "sql"
      code: |
        -- Procedure to create a case with primary applicant atomically
        DELIMITER $$

        CREATE PROCEDURE create_immigration_case(
          IN p_case_number VARCHAR(50),
          IN p_case_type_id INT,
          IN p_filing_date DATE,
          IN p_first_name VARCHAR(100),
          IN p_last_name VARCHAR(100),
          IN p_date_of_birth DATE,
          IN p_nationality VARCHAR(100),
          IN p_passport_number VARCHAR(50),
          OUT p_case_id INT,
          OUT p_person_id INT
        )
        BEGIN
          DECLARE EXIT HANDLER FOR SQLEXCEPTION
          BEGIN
            ROLLBACK;
            RESIGNAL;
          END;

          START TRANSACTION;

          -- Check if person already exists by passport
          SELECT person_id INTO p_person_id
          FROM persons
          WHERE passport_number = p_passport_number
          LIMIT 1;

          -- Create person if not exists
          IF p_person_id IS NULL THEN
            INSERT INTO persons (first_name, last_name, date_of_birth, nationality, passport_number)
            VALUES (p_first_name, p_last_name, p_date_of_birth, p_nationality, p_passport_number);
            SET p_person_id = LAST_INSERT_ID();
          END IF;

          -- Create case
          INSERT INTO cases (case_number, case_type_id, filing_date, status)
          VALUES (p_case_number, p_case_type_id, p_filing_date, 'OPEN');
          SET p_case_id = LAST_INSERT_ID();

          -- Link person to case as primary applicant
          INSERT INTO case_persons (case_id, person_id, role, is_primary)
          VALUES (p_case_id, p_person_id, 'APPLICANT', TRUE);

          -- Update denormalized counter
          UPDATE persons SET active_case_count = active_case_count + 1
          WHERE person_id = p_person_id;

          -- Create initial status history entry
          INSERT INTO case_status_history (case_id, old_status, new_status, changed_by)
          VALUES (p_case_id, NULL, 'OPEN', USER());

          COMMIT;
        END$$

        DELIMITER ;

  learnings: |
    1. **Normalization is a default, not a religion.** Storing `active_case_count` on persons saves an aggregate query on every listing, at the cost of keeping that copy consistent.

    2. **Relationships have attributes.** `case_persons` began as just two IDs. Then `role`, `is_primary` and `relationship` turned up, and they belong to the link, not to the person or the case.

    3. **Date ranges need the right index.** Putting status alongside `expiration_date` in a composite index is what got rid of the filesorts.

    4. **ENUM or foreign key depends on how stable the list is.** `status` and `role` are ENUMs because they rarely change. `case_type` and `document_type` are foreign keys because they will.

    5. **Let the database say no.** Foreign keys reject a case with a made-up case type, and NOT NULL dates and ENUM statuses keep document rows trustworthy.

    6. **Build the audit trail and the transactions early.** Creating a case touches several tables, and a failure halfway would leave orphaned rows. Retrofitting a history table later is painful.
---
The part I'd point at is `case_persons`: a junction table that grew up and started carrying the role, the primary flag and the relationship. A stored procedure creates the person if needed, the case, the link and the first history row in one transaction, or none of them. The one thing I denormalized on purpose is a case count, and it comes with the upkeep you'd expect.
