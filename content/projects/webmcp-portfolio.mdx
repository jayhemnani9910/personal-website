The emerging WebMCP browser API takes a different route: a site registers structured tools that an agent calls directly, with JSON Schema inputs and typed JSON results. This project works out what it takes to expose a real, content-heavy site through that API."

deepDive:
  context: "The WebMCP proposal lets a website expose tools to an AI agent the same way an MCP server exposes them to a model: a name, a description, a JSON Schema for inputs, and a handler that returns structured data. Instead of screenshotting or scraping this site, an agent can call search_projects or get_resume and get clean JSON back. The API is new, navigator.modelContext behind a flag in Chrome 146, so part of the work was simply learning how the registration lifecycle behaves on a real Next.js site rather than inventing a new data layer."
  architecture: "The integration is two layers. A server component (WebMCPLoader) reads all site data at the server, projects from the MDX content loader, the resume object, social links from site config, and lab experiments, and shapes it into one typed SiteData object. It passes that to a client component (WebMCPProvider) which, on mount, checks whether navigator.modelContext exists and, if so, registers the eight tools plus a site-context blurb, returning a cleanup that unregisters them. Each tool is a name, a human-readable description, a JSON Schema input definition, and an async handler that filters or transforms the in-memory SiteData. Six read tools return JSON; two write tools mutate the DOM and localStorage and fire a storage event so the site's React contexts react live."

  keyDecisions:
    - decision: "Expose tools through WebMCP rather than an llms.txt file or a separate API"
      reasoning: "WebMCP gives an agent typed, callable tools inside the page it is already on, with JSON Schema inputs and structured returns, which removes the scraping and clicking layer entirely. A static text file or a standalone REST API would not be discoverable from the browsing session."
      alternatives: "llms.txt (static, not interactive); a public REST API (extra surface to host, not tied to the page the agent is viewing)."
    - decision: "Progressive enhancement behind an availability guard"
      reasoning: "The API is behind a flag in one browser channel, so the site has to work for everyone and add tools only when navigator.modelContext is present. The provider checks first, registers nothing otherwise, and unregisters on unmount."
      alternatives: "Assume the API exists (breaks the site for normal visitors); feature-detect once globally (misses the React mount and unmount lifecycle)."
    - decision: "Load data server-side, register client-side"
      reasoning: "Tool handlers need the full project and resume data, but registration must run in the browser where navigator lives. A server component assembles the data once and a client component registers the tools over it, so handlers operate on in-memory data with no per-call fetch."
      alternatives: "Fetch inside each handler (a network round-trip per call); hand-inline the data in the client bundle (duplicates the content loader)."

        useEffect(() => {

    - title: "Two of the tools change the page, not just read it"
      language: "typescript"
      code: |
        // toggle_theme handler
        const current = document.documentElement.getAttribute("data-theme") || "dark";
        const newTheme =
          args.theme === "light" || args.theme === "dark"
            ? args.theme
            : current === "dark" ? "light" : "dark";

        document.documentElement.setAttribute("data-theme", newTheme);
        localStorage.setItem("theme", newTheme);
        // storage event so the site's React ThemeContext picks it up
        window.dispatchEvent(new StorageEvent("storage", { key: "theme", newValue: newTheme }));
        return { previous: current, current: newTheme };
      explanation: "Six tools read; two write. An agent can flip the theme or switch presentation mode, which dispatches a storage event the site's React contexts already listen for, so WebMCP becomes a control surface rather than only a query layer."

This portfolio registers structured tools through the WebMCP browser API (`navigator.modelContext`), so an AI agent can query it directly instead of scraping the DOM. Eight tools let an agent search every project, read the full resume, list skills and lab experiments, and even change the site's theme or presentation mode, each with a JSON Schema for inputs and typed JSON results. The site works normally for everyone; the tools register only when the browser exposes the API (Chrome 146+ with the WebMCP flag) and unregister on cleanup. Site data is gathered server-side and handed to a client component that does the registration in the browser.
