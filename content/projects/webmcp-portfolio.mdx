challenge: "An agent using a website normally scrapes the DOM and clicks buttons, and that breaks the moment a layout changes. WebMCP, a W3C community group draft, takes a different route: the site registers tools with JSON Schema inputs, and the agent calls them directly. The catch with building on a draft is that it moves. My first version used provideContext and clearContext. Both got removed, and by the time I rewrote it, none of the tools registered and flagged Chrome 143-151 crashed the page."
solution:
  - "This site registers 7 tools through document.modelContext: project search, single-project lookup, resume, skills, contact, lab experiments, and one that changes the page (reader mode)."
  - "Each tool has a JSON Schema for its inputs and returns JSON with full URLs, so an agent gets structured data instead of rendered HTML."
  - "Everyone else gets the normal site. The tools register only when the browser has the API (Chrome with the WebMCP testing flag on), and aborting one signal on cleanup removes them all."
  - "Site data is built once into a static /site-data.json. The browser fetches it, and the tool code, only after it finds the API, so other visitors download neither."
impact:
  - "An agent can search every project, pull the resume, list skills and see what's in the lab, all as JSON. That includes this page, through get_project."
  - "One tool has a real side effect: switch_mode turns on reader mode live, so an agent can operate the site as well as read it."
  - "The rewrite also shrank every page's HTML, because the tool data stopped being inlined. At the time, /blog went from 102 KB to 43 KB and the 404 page from 86 KB to 27 KB."
  - "Registration was checked in Chromium 151 with the flag on, and the tests run every tool against a fake modelContext. You need that flag to see any of this, so treat it as an early experiment."
deepDive:
  context: "WebMCP lets a website offer tools to an AI agent the way an MCP server offers them to a model (MCP being the common protocol for handing tools to models): a name, a description, a JSON Schema for inputs, and a callback that returns structured data. Instead of screenshotting this site, an agent can call search_projects or get_resume and get clean JSON. The API is still a draft behind a flag, so much of the work was keeping up with it and learning how registration behaves on a real Next.js site. I wasn't inventing a new data layer."
  architecture: "There are two layers. A static route (/site-data.json) is built once at build time from the MDX projects, the resume, social links and lab experiments. A client component (WebMCPProvider) checks on mount whether document.modelContext exists. Only if it does, it fetches that file and the tool module, then registers the seven tools with one AbortSignal. Its cleanup aborts the signal, which removes them all. Each tool is a name, a description, a JSON Schema and an async execute callback that filters the in-memory data. Six read tools return JSON. The write tool changes the DOM and localStorage and fires readermodechange, an event the site already listens for, so the page updates live."

  keyDecisions:
    - decision: "Expose tools through WebMCP rather than an llms.txt file or a separate API"
      reasoning: "WebMCP gives an agent typed, callable tools inside the page it's already on. A static text file can't be called, and a separate API wouldn't show up in the browsing session."
      alternatives: "llms.txt (static, not interactive); a public REST API (extra surface to host, not tied to the page the agent is viewing)."
    - decision: "Progressive enhancement behind an availability guard"
      reasoning: "The API sits behind a flag, so the site has to work for everyone and add tools only when document.modelContext is there. That guard is why normal visitors never saw the breakage when the draft moved. Only flagged Chrome did."
      alternatives: "Assume the API exists (breaks the site for normal visitors); feature-detect once globally (misses React's mount and unmount lifecycle)."
    - decision: "Build the data once, fetch it only when the API exists"
      reasoning: "The tools need all the project and resume data, but only a browser with the API can use them. So it's a static file fetched after detection, with no cost for everyone else and no network call per tool call."
      alternatives: "Pass the data down from a server component (puts it in every page's HTML, which is what the old version did); fetch inside each execute (a round-trip per call)."
  codeSnippets:
    - title: "A tool is a name, a JSON Schema, and an execute callback"
      language: "typescript"
      code: |
        mc.registerTool({
          name: "search_projects",
          description: "Search Jay's projects by query, technology, tags, or domain.",
          inputSchema: {
            type: "object",
            properties: {
              query: { type: "string", description: "Free-text across title, summary, tech" },
              tech: { type: "string", description: "Filter by technology" },
              featured_only: { type: "boolean", description: "Only featured projects" },
            },
          },
          execute: async (args) => {
            let results = [...data.projects];
            // filter by query / tech / tag / domain / featured ...
            return {
              count: results.length,
              projects: results.map((p) => ({
                id: p.id, title: p.title, tech: p.tech,
                url: `https://jayhemnani.in/projects/${p.id}`,
              })),
            };
          },
        }, { signal });
      explanation: "Every tool has the same shape: name, description, input schema, and an async callback over the in-memory data. The agent gets JSON back and never touches the HTML."
    - title: "Progressive enhancement: register only when the API exists"
      language: "tsx"
      code: |
        useEffect(() => {
          if (!document.modelContext) return;   // API is behind a flag; do nothing otherwise
          const controller = new AbortController();

          (async () => {
            const [{ registerWebMCPTools }, res] = await Promise.all([
              import("@/lib/webmcp"),
              fetch("/site-data.json", { signal: controller.signal }),
            ]);
            await registerWebMCPTools(await res.json(), controller.signal);
          })();

          return () => controller.abort();      // unregisters every tool
        }, []);
      explanation: "No API, no download, nothing happens. With it, the data and tool code load and the tools register. Removing them is one abort, because the draft dropped its unregister call and made the AbortSignal the way out."
    - title: "One of the tools changes the page"
      language: "typescript"

        // switch_mode execute
        const on = args.mode === "reader";
        setReaderMode(on); // sets data-reader, saves it, fires readermodechange
        return { mode: on ? "reader" : "default", reader: on };
      explanation: "An agent can turn on reader mode, and the motion on the page stops right away. The footer toggle uses the same function, so the agent gets no special path."

Here's my favourite detail: a test reads this very file and fails if I state the wrong tool count. The number has changed before, when the theme tool left with the dark theme, and a portfolio that lies to agents about its own tools would be a bit embarrassing. Every description is also written for a reader that's a machine, so the schema examples point at values that actually exist, and an agent doesn't waste a call on a filter that returns nothing.
