deepDive:
  context: "The WebMCP proposal lets a website expose tools to an AI agent the same way an MCP server exposes them to a model: a name, a description, a JSON Schema for inputs, and an execute callback that returns structured data. Instead of screenshotting or scraping this site, an agent can call search_projects or get_resume and get clean JSON back. The API is new, document.modelContext behind a flag in Chrome 146, so part of the work was simply learning how the registration lifecycle behaves on a real Next.js site rather than inventing a new data layer."
  architecture: "The integration is two layers. A static route (/site-data.json) is built once at build time: it reads projects from the MDX content loader, the resume object, social links from site config, and lab experiments, and shapes them into one typed SiteData object. A client component (WebMCPProvider) checks on mount whether document.modelContext exists. Only if it does, it fetches that file and the tool module, then registers the seven tools with one AbortSignal; its cleanup aborts the signal, which unregisters them all. Each tool is a name, a human-readable description, a JSON Schema input definition, and an async execute callback that filters or transforms the in-memory SiteData. Six read tools return JSON; the write tool changes the DOM and localStorage and fires readermodechange, an event the site already listens for, so the page updates live."

  keyDecisions:
    - decision: "Expose tools through WebMCP rather than an llms.txt file or a separate API"
      reasoning: "WebMCP gives an agent typed, callable tools inside the page it is already on, with JSON Schema inputs and structured returns, which removes the scraping and clicking layer entirely. A static text file or a standalone REST API would not be discoverable from the browsing session."
      alternatives: "llms.txt (static, not interactive); a public REST API (extra surface to host, not tied to the page the agent is viewing)."
    - decision: "Progressive enhancement behind an availability guard"
      reasoning: "The API is behind a flag in one browser channel, so the site has to work for everyone and add tools only when document.modelContext is present. The provider checks first, registers nothing otherwise, and aborts the tools' signal on unmount."
      alternatives: "Assume the API exists (breaks the site for normal visitors); feature-detect once globally (misses the React mount and unmount lifecycle)."
    - decision: "Build the data once, fetch it only when the API exists"
      reasoning: "The tools need the full project and resume data, but only a visitor whose browser has the API can use them.       alternatives: "Pass the data down from a server component (puts it in every page's HTML for every visitor); fetch inside each execute (a network round-trip per call)."

    - title: "Progressive enhancement: register only when the API exists"
      language: "tsx"
      code: |
        useEffect(() => {
          if (!document.modelContext) return;   // API is behind a flag; do nothing otherwise
          const controller = new AbortController();

          (async () => {
            const [{ registerWebMCPTools }, res] = await Promise.all([
              import("@/lib/webmcp"),
              fetch("/site-data.json", { signal: controller.signal }),
            ]);
            await registerWebMCPTools(await res.json(), controller.signal);
          })();

          return () => controller.abort();      // unregisters every tool
        }, []);
      explanation: "The site renders normally for every visitor. The data and the tool code are fetched, and the tools registered, only when document.modelContext is present. The effect's cleanup aborts the signal they were registered with, which unregisters them, so the lifecycle follows React's mount and unmount."

This portfolio registers structured tools through the WebMCP browser API (`document.modelContext`), so an AI agent can query it directly instead of scraping the DOM. Seven tools let an agent search every project, read the full resume, list skills and lab experiments, and even switch the site into reader mode, each with a JSON Schema for inputs and typed JSON results. The site works normally for everyone; the tools register only when the browser exposes the API (Chrome 146+ with the WebMCP flag) and unregister on cleanup. The site data is a static file built at build time, fetched only by browsers that have the API.
