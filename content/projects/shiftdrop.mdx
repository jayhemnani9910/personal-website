challenge: "Converting a file usually means uploading it to a website you don't trust or installing an app you use for ten seconds. I wanted it to happen mid-drag, right where the file already is. The catch: a Wayland app can't see another app's drag at all, and Shift means \"move\" in Nautilus and Explorer, so a careless drop target would get your original deleted."
solution:
  - "Hold Shift during a drag and the wheel opens under the pointer. Add Ctrl and it becomes tools instead: compress, trim, strip metadata, resize and more. Results land next to the original and never overwrite anything."
  - "On GNOME, a small Shell extension sees the drag and the Shift key, then asks the GTK4 app over D-Bus to show the wheel. On Windows, a low-level mouse hook does that job, and the wheel is an OLE drop target drawn with Direct2D."
  - "One shared Rust core decides what each file can become, plans the exact ffmpeg, magick or gs commands, and runs them with progress and cancel. If a job dies, its half-written file gets removed."
  - "GitHub Actions builds a .deb, a one-line install tarball and a Windows installer on each version tag."
impact:
  - "Drag, Shift, drop. No upload and no account. Conversions run on your own machine and send nothing anywhere."
  - "When the codec already fits the new container, video is copied instead of re-encoded: a 116 s clip to MKV in 0.4 s. Images convert four at a time, so 16 screenshots to WebP took 0.47 s instead of 1.29 s. Those numbers come from one machine (8 cores, Intel GPU)."
  - "Everything after the drop is shared code across the two desktops. Only drag detection and drawing differ."
  - "Limits: Linux needs GNOME 49+ on Wayland. The Windows installer isn't signed yet, so SmartScreen warns you, and a drag from a program running as administrator can't reach the wheel."
deepDive:
  context: "This began as a Linux port of a Mac app called Open Tangerine, and its formats and conversion matrix came from there. Then it got its own format rules and encoder settings, a rewrite from Python to Rust, and a Windows version. The interaction stayed the same throughout: the wheel exists only during a drag you were already doing. Behind it sit the usual open-source converters, with encoder settings picked by measuring speed and SSIM (a score for how close the output looks to the source) on a real phone clip."
  architecture: "A Rust library holds everything that isn't a window: what a file is and what it can become, filtered by the converters and ffmpeg encoders this machine actually has; the commands each job needs; and a job runner that streams ffmpeg progress, checks for cancel every 100 ms, falls back from GPU to CPU, and records outputs so a killed job's leftovers get cleaned up on the next start. Two front ends drive it. On Linux, the Shell extension calls the GTK4 app over D-Bus, and the wheel is an ordinary GTK drop target. On Windows, a mouse hook on its own thread spots the drag, and the wheel is a layered window that only ever accepts a copy, so Explorer can't delete the source."

  keyDecisions:
    - decision: "Only ever accept a drop as a copy"
      reasoning: "Shift means move in both Nautilus and Explorer. Accept a move and the source app deletes your original after the drop. So it's copy or nothing."
      alternatives: "A different modifier (clashes with existing shortcuts); accept moves and hope (loses files)."
    - decision: "Don't draw the wheel until it knows it's a file drag"
      reasoning: "Windows lets drags fall through fully transparent pixels, so the wheel starts as a disc painted at alpha 1 out of 255: invisible to you, solid to Windows. It's drawn only once the drag turns out to carry files. Text and other drags get let through."
      alternatives: "Show the wheel on every Shift-drag (gets in the way of selecting text)."
    - decision: "Copy streams when the target can hold them"
      reasoning: "Many container changes don't need a re-encode. Copying scored SSIM 1.000 on the test clip and takes about a second. Re-encoding is kept for codecs the target can't hold."
      alternatives: "Always re-encode (slow and lossy)."

On Windows, run the installer; it starts ShiftDrop at sign-in, adds it to Send To, and can install the converters with winget. On Ubuntu, `sudo apt install ./shiftdrop_amd64.deb`. Then drag a file and hold Shift. The tests check the planned commands and run real conversions on tiny generated files, and CI runs the planned-command tests on both Linux and Windows.
