challenge: "Flights, hotels, cars, deals, billing and notifications all scale and fail differently, and cramming them into one service ties their deploys together. I wanted to see how far that separation could sensibly go. The hard part is the line between two kinds of call: what can happen later over events, and what needs an answer right now."
solution:
  - "A TypeScript monorepo holding 14 services: an API gateway, services for flights, hotels, cars, booking, billing and users, plus notifications, admin analytics, a deals worker, an airport resolver, external adapters, a Python AI concierge and a React/Vite client."
  - "Kafka for the asynchronous parts: deals fan out on deal.events, and payments and confirmations have their own topics. Booking still calls the flight, hotel and car services over HTTP to look items up, so it isn't events all the way down."

  - "Services on Kafka can go offline and catch up from the log. Booking's HTTP lookups can't: if flights is down, that lookup fails."
  - "Honest limits: the manifests cover 11 of the 14 services (not the client, airport resolver or external adapters), the repo has no record of a real cluster run, only five services have unit tests, and the Pages demo is the client in demo mode with no backend."

Behind it sit flights, hotels, cars, booking, billing and user, each its own Express app with its own Dockerfile. Kafka carries the asynchronous work: the deals worker publishes deal.events, the flight, hotel and car services each consume it on their own consumer group, and payments and confirmations travel on their own topics. Booking looks items up over HTTP. Around that are notifications, admin analytics, an airport resolver, external adapters for third-party APIs, and two Python services: the deals worker and a concierge using a local Ollama model. Storage is MongoDB and MySQL depending on the service, with Redis for caching, and @kayak/shared gives everyone the same types. The repo has Kubernetes manifests for 11 services, Nginx, and GitHub Actions for CI, CD and the Pages build."

  keyDecisions:
    - decision: "Fourteen services in one monorepo with shared types"
      reasoning: "Lots of small services can drift apart on event schemas. A monorepo with one shared types package keeps the contract in one place, so services can deploy separately and still agree."
      alternatives: "A repo per service (schema drift, painful cross-cutting changes); one big service (no independent deploys, the thing I was trying to avoid)."
    - decision: "Use Kafka events where async fits, HTTP where it doesn't"
      reasoning: "Direct HTTP ties services' availability together. With Kafka, a consumer can go offline and catch up from the log. But booking needs an answer from flights, hotels and cars before it can carry on, so those lookups stay as HTTP calls."
      alternatives: "HTTP everywhere (tight coupling); coordinating through a shared database (couples services through their data)."
    - decision: "Pick storage per service"
      reasoning: "Flights, hotels, cars, booking and billing run on MySQL, admin analytics and the deals worker use MongoDB, and Redis handles caching. The MySQL services all share one database, so data ownership is looser than the split suggests."
      alternatives: "One database for all data (a shared bottleneck and a coupling point)."

        export class CarDealConsumer {
          constructor(db: mysql.Connection, redis: any) {
            this.kafka = new Kafka({
              clientId: 'cars-svc',
              brokers: [process.env.KAFKA_BROKERS || 'localhost:9092'],
            });
            this.consumer = this.kafka.consumer({ groupId: 'cars-deals-consumer' });
          }

          async start(): Promise<void> {
            await this.consumer.connect();
            await this.consumer.subscribe({ topic: 'deal.events', fromBeginning: false });
            await this.consumer.run({
              eachMessage: async ({ message }) => {
                const event: DealEvent = JSON.parse(message.value?.toString() || '{}');
                if (event.type === 'car') await this.handleCarDeal(event);
              },
            });
          }
        }

The interesting decision is where the events stop. Deals fan out over Kafka, so the worker that publishes never needs to know who's listening, while booking asks flights, hotels and cars directly because it can't carry on without an answer. A shared package keeps all 14 services on the same event and model types, and its name, @kayak/shared, gives away the course brief this started from. It's my own repo, separate from the team version.
