challenge: "Fixing types, nulls, duplicates and date formats is the unglamorous core of data work, and every fix can be checked. That makes it a good thing to train an agent on, if you can frame it properly. It needs a small set of moves, observations an agent can reason over, and a reward that can't be farmed by changing cells for the sake of it."
solution:
  - "An RL environment built on OpenEnv's Action and Observation base types, so it speaks the hackathon's standard protocol rather than a protocol of my own."
  - "Seven typed cleaning moves: replace_value, convert_type, fill_missing, remove_duplicates, drop_rows, standardize and parse_date."
  - "Each observation has the current rows, per-column types and null counts, the score so far, how many issues are fixed, and feedback on the last action."
  - "Four graded tasks, from a 5-row type-fixing warm-up to a 15-row mix of everything, served over FastAPI and packaged in Docker to run as a Space."
impact:
  - "Each step's reward is the change in score. Fix something and you gain. Break something and you lose. Busywork earns nothing."
  - "35 test functions, 29 of them on the graders. My own plan notes said the graders had never been mechanically verified, and a scorer nobody has checked isn't worth much."
  - "The README lists baseline LLM scores of about 0.78, 0.83, 0.58 and 0.60 across the four tasks. The repo has no run logs behind those numbers, and nothing here is a trained agent."
  - "One wart I'd fix: the evaluator rejected scores of exactly 0 or 1, so I clamped them to 0.01-0.99. The done check still wants 1.0, so a perfect run now keeps going until the step limit."

  keyDecisions:
    - decision: "Build to the OpenEnv spec instead of a custom harness"
      reasoning: "A one-off environment only works with its own glue code. OpenEnv was the point of the hackathon, and subclassing its types means the standard client and validator know what they're looking at. A few of my commits exist purely to satisfy openenv validate."
      alternatives: "A bespoke gym-style API (works in isolation, but not with the OpenEnv tooling the hackathon was about)."
    - decision: "A small typed action space, not free-form edits"
      reasoning: "Arbitrary transformations are hard to score and easy to game. Seven explicit moves stay checkable and map onto what a data engineer actually does."
      alternatives: "Free-form code or SQL actions (unsafe and hard to reward); a single 'clean' action (nothing to learn)."
    - decision: "Score per check passed, not per action taken"
      reasoning: "Rewarding actions would reward busywork. Rewarding the change in checks passed means thrashing gains nothing and breaking a passing check costs you."
      alternatives: "Reward per action (encourages noise); all-or-nothing at the end (sparse, hard to learn from)."
  codeSnippets:
    - title: "An OpenEnv-typed action space"
      language: "python"
      code: |
        from openenv.core.env_server.types import Action, Observation

        class DataCleanAction(Action):
            action_type: Literal[
                "replace_value", "convert_type", "fill_missing",
                "remove_duplicates", "drop_rows", "standardize", "parse_date",
            ]
            column: Optional[str] = Field(None, ...)
            target_type: Optional[Literal["int", "float", "str"]] = Field(None, ...)
            method: Optional[Literal["lowercase", "trim", "title_case", "uppercase"]] = ...
            # plus value / old_value / new_value / row_indices / subset_columns

        class DataCleanObservation(Observation):
            current_data: Optional[List[Dict[str, Any]]] = Field(None, ...)
            column_info: Optional[Dict[str, Dict[str, Any]]] = Field(None, ...)
            total_issues: int = 0
            issues_fixed: int = 0
            score: float = Field(0.0, description="Current score [0.0-1.0]")
            done: bool = False
      explanation: "A closed list of seven moves, so an agent can't improvise its way out of the scoring. The observation gives it the data, column stats and progress. The score's description still says 0.0-1.0, from before the clamp."
    - title: "The environment applies a typed action"
      language: "python"
      code: |
        def _apply_action(data, action: DataCleanAction):
            """Apply an action to the data. Returns (new_data, result_message)."""
            if action.action_type == "convert_type":
                for row in data:
                    val = row.get(action.column)
                    if val is None:
                        continue
                    if action.target_type == "int":
                        row[action.column] = int(float(str(val)))
                    elif action.target_type == "float":
                        row[action.column] = float(str(val))
                    elif action.target_type == "str":
                        row[action.column] = str(val)
                return data, f"Converted values in '{action.column}' to {action.target_type}"
            # ... one branch per action type, each returning a result message
      explanation: "One branch per move, each returning a message an agent can read. In the real handler, values that won't convert are counted and reported, with a hint to fix those first."

The tasks are small, hand-written tables, the hardest being 15 rows of customer orders, so it isn't real-world scale and it isn't trying to be. The work was in the graders, which needed to tell a cleaned table from one that only looks different. It's also a nice small lesson in how specs bite: I had to change the port and clamp the scores to suit the validator and evaluator.
