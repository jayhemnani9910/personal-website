challenge: "Moving money looks like one operation. In SQL it's a sanity check, an insert and two updates, and every one of them has to agree with the others. This was a small app for learning exactly that."
solution:
  - "A transfer form (debit account, beneficiary account, amount) that checks the input and the balance, then moves the money."
  - "A history page showing the latest 100 transfers, newest first."
impact:
  - "My first pass at forms, server-side validation and SQL writes against a real schema. There's no login, so anyone who opens Sparks Bank can spend anyone's money. Please don't deposit anything."

deepDive:
  context: "One of my first complete web apps, built in February 2021 as a task for The Sparks Foundation, which the footer credits. The scope is small on purpose: a home page, a transfer form and a history page. I used it to learn the request-response cycle and how a page reads and writes MySQL."

  architecture: |
    Four procedural PHP files over one MySQL database, no framework:

    - **index.php**: the home page, linking to the form and the history.
    - **transfermoney.php**: shows the form and, on POST, runs the transfer.
    - **transactionhistory.php**: lists the latest 100 transfers.
    - **database.php**: opens the mysqli connection the other pages share.

    The queries use an ACCOUNTS table (account number and balance) and a TRANSACTIONS table (debit account, beneficiary account, amount, time added).

  components:
    - name: "Transfer form"
      purpose: "Takes the two account numbers and an amount, and marks the field that was wrong if an account or the amount is rejected."

    - name: "Transfer logic"
      purpose: "Rejects a zero amount or an unknown account, refuses anything that would leave the sender below 1,000, then records the transfer and updates both balances."

    - name: "Transaction history"
      purpose: "Reads TRANSACTIONS newest first and shows the account number on each side. The query can page, but the page always asks for the first 100 rows."

  dataFlow: |
    1. The form posts back to transfermoney.php
    2. The amount can't be zero, the debit account must exist, and the sender must keep at least 1,000
    3. A row goes into TRANSACTIONS; if the beneficiary doesn't exist, the insert fails and the page says so
    4. Two UPDATE queries debit the sender and credit the beneficiary
    5. The page shows success, or an error next to the bad field

  keyDecisions:
    - decision: "Procedural PHP over a framework"
      rationale: "I wanted the fundamentals before abstractions like Laravel, and it's a good way to appreciate what frameworks do for you."
      tradeoff: "Each page mixes HTML, form handling and SQL; only the database connection is shared."

    - decision: "Hand-written SQL instead of an ORM"
      rationale: "The point was to learn SQL itself: an insert that looks up account ids with sub-selects, the balance updates, and the history query."
      tradeoff: "Queries are built by concatenating form input rather than using prepared statements, and the insert and the two updates run without a database transaction."

    - decision: "Minimal frontend styling"
      rationale: "The focus was the server side. Bootstrap's stylesheet and a few inline styles make it usable, not polished."
      tradeoff: "No client-side validation: every check happens after the form is submitted."

  learnings:
    - learning: "Validation belongs on the server"
      description: "Every check runs in PHP after the form posts, so a hand-built request can't skip it. Though the checks need to be right: only zero is refused, so by the code a negative amount gets through and pulls money out of the beneficiary. A refused low-balance transfer also shows no message."

    - learning: "Security fundamentals"
      description: "Concatenating form input into SQL, as this code does, leaves it open to SQL injection. Prepared statements are the fix."

    - learning: "Why atomicity matters for money"
      description: "The transfer is an insert and two updates. If one fails partway, the balances and the history disagree. One database transaction is what keeps them in step."
---
A very small bank in procedural PHP, and a fair picture of me in early 2021 finding out what happens between a form and a database. It checks the amount, both accounts and the minimum balance before it moves anything, and all of that lives in one file with the HTML.
